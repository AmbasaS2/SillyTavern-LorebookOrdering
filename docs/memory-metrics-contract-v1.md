# STLO recall and budget efficiency (experimental contract v1)

Scope: STLO owns search/decision/batching/admission/budget efficiency. WorldInfo Info owns final RP lore list, reason and actual-inclusion evidence, per-entry/book/activation-category injection measures. Memory Books collection statistics and unified cross-extension cost dashboard are excluded. No change to companion repositories.

## Existing path and measurements

STLO's existing Jev report uses candidate counts, completed batches, accepted and activated counts, estimated input and provider-reported input, and request duration. The existing scan uses getTokenCountAsync(entry.content + newline) to enforce book/world/Jev ceilings. The new report reuses that path: budget costs are host tokenizer results for individually counted **full** entry text including its trailing newline, not provider usage or the exact post-regex RP payload. Originally ignoreBudget entries are not charged to the book cap; Jev-managed non-outlet entries can still consume the Jev cap. A missing count is not zero; show known subtotal + number unmeasured, no invented remainder. An uncapped book uses the shared cap; never assign the entire global cap to each book. Final scan stage and actual WORLD_INFO_ACTIVATED are distinguished; final activation is not proof of RP inclusion. All confirmed RP counts use actual rendered text and only the selected Jev subset. Sum of individual rendered counts is not tokenization of a joined prompt. No full-book scans or requests for reporting, no polling, no extra model calls, no persisted run history.

Provider usage is parsed only from reported fields; input/output/cache-read/cache-write may be absent independently. Report coverage per successful request, attempted estimates and request elapsed time separately. Cache counters are not added to input or assumed free; actual charge and missing failed-attempt usage are unknown. Native vector pass and dry candidate-scan timing are not vector provider token usage. Recent eight completed/cancelled runs in this chat/session retain numeric summaries, never lore or prompts.

## Optional companion interface

`globalThis.STLOMemoryMetrics`, version 1. Existing `STWII.recordStloJevRecall(lists, appliedKeys)` unchanged. Read the context during the real generation's active recall or budget scan; retain its opaque handle for the current generation only. It survives completion until next generation or scope invalidation. A chat/character/group/speaker or tokenizer change invalidates it. If missing/unsupported/error, the viewer follows its own existing measurement path.

- `context()` → `{generation,tokenizer}` or null. The generation handle is an opaque same-realm object (do not serialize or reconstruct). Tokenizer is STLO's current host tokenizer identity, not a model usage claim. Unknown or dynamic remote tokenizer disables sharing. Use only for the same host tokenizer function; do not use with a custom tokenizer.
- `lookup({generation,tokenizer,target,text,padding})` → cached count or null, no work. For an individual entry target is JSON.stringify([world, uid]) using the same world and UID types as the host. Text must be the exact tokenizer input including whitespace/newline and all transformations. Padding must match (undefined for existing STLO budget calls).
- `await measure({generation,tokenizer,target,text,padding})` → same host tokenizer count or null. Call only instead of an already-planned viewer measurement; coalesces pending work for the exact same generation/target/text/tokenizer/padding. The bounded ledger retains at most 2048 records and 2M characters and expires on next generation/chat. A joined aggregate is a different target (e.g. 'aggregate:wi') and must not reuse a sum of individual budget counts. The current viewer calculates one joined rendered count on open, so that existing aggregate cannot be treated as per-entry injection measurements.
- `selection({generation,key})` → positive Jev decision, observed include score, candidate route, budget outcome, activated true/false/null. No generated rationale. Not a final payload proof.
- `publishInjection({generation,tokenizer,records,complete})` → boolean. Companion calls only with genuinely verified final payload evidence. Records are `{key,status:'confirmed',text:exactRenderedIndividualTokenizerInput}`, `{key,status:'excluded'}` or `{key,status:'unknown'}`. Do not infer confirmation from ordinary WORLD_INFO_ACTIVATED, arbitrary substring matches or saved flags. For confirmed entries use measure/lookup on same exact key and text before publishing; no additional call is made by STLO. Complete true means every relevant actually activated Jev key was accounted for, including excluded/unknown. STLO filters to its accepted+activated keys, rejects duplicate records, stale generation and incompatible tokenizer. A confirmed entry without cached measurement stays unmeasured; missing/unknown entries prevent a complete total. No text is stored in numeric history. A late report only updates matching latest generation. No companion installed: normal STLO operation, book budget report and selected activation counts, RP confirmed token field explicitly unmeasured. This is intentional rather than claiming activation equals final injection.

## Adoption gates

Unit tests cover missing/zero usage, dedup, exact text/tokenizer/padding, scope and stale handles, failure eviction, cap/remaining and final scan rejection, independent existing modes, optional measurement and payload receipt, session history. Actual WII adoption requires a coordinated companion implementation and same-host isolated tests (both alone/together, identical descriptor one tokenization, transformed text distinct, missing and late report, mobile/desktop). No changes to main, release or operating installation. Preserve current selection quality experiments and separately validate the original implicit-habit replay; no quality or total savings guarantee.

Safety follow-up: a real activation key mismatch invalidates the budget snapshot rather than attributing it to the wrong activation list. An unconfirmed scan is explicitly provisional; final recall-budget total stays unknown until observed. Cancellation invalidates the generation handle. A count that completes after a tokenizer/scope change cannot be reused. Show shared Jev cap/use/remainder and confirmed/excluded/unknown RP counts separately.

### Compatibility with Lore Insight v1 (WorldInfo Info 921ce25)

STLO now consumes optional `STWII.loreTokenCountV1` (`apiVersion: 1`, `count(text)`) for the existing unpadded host counter path in known OpenAI tokenizer contexts. Exact input strings include the same newline; different strings/padding never substitute. The viewer owns its generation/tokenizer scoped text cache and calls the host directly. STLO retains its entry-key ledger and optional `STLOMemoryMetrics` selection/publication interface. Missing, incompatible, null or throwing viewer falls back to the normal host count. The consumer does not wrap or overwrite the viewer's API. Recursive callback to `measure` for the same in-flight string returns null instead of deadlocking. A changed STLO generation/scope/tokenizer invalidates the result. This improves reuse of budget counts by current Lore Insight; its final payload evidence publisher and detailed selection consumer remain a separate implementation in that extension. Do not claim final RP attribution from cached text alone.

Report layout: the existing popup has a compact status/funnel overview, one open efficiency section, collapsible book budgets, history, decision, partial-injection and request details. Every original metric is preserved; duplicate eligible count is removed. Opening or expanding a report does not count tokens, query lorebooks, save settings or send a model request. Existing theme variables and scoped mobile layout are used.

### Main integration and lifecycle follow-up (2026-11-27)

Owner approved merging the source to main before release; experimental options stay opt-in. No release, manifest, installed settings, or storage-schema change. Budget-only reports show actual native activation and STLO structural exclusions by book and in total, separately from Jev assessment and final RP evidence. They do not claim Jev usage or RP injection. The generation scope is invalidated on speaker/chat change; a returned-to speaker does not resurrect an old ledger. Concurrent identical strings for different entry keys share the pending companion count within the generation, while entry-specific ledger attribution remains distinct. If a viewer attempts a recursive call into the same pending companion path, it receives an existing cached value or null instead of a cycle. Companion count must use the host directly (as current WII does). The main verification workflow runs the same tests on main and follow-up PRs. Final RP evidence publication still requires a compatible consumer/publisher in WII.
